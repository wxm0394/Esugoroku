## Executive Summary

An engineering audit of `mobile/js/boards.js` and `mobile/js/core.js` against `TEST_REPORT.md` (and `tools/test_browser_e2e.py` / `docs/GAME_DESIGN_SPEC_V1.1-V2.0.md`) revealed that while the JavaScript rules engine and board data were expanded to **25 / 25 / 24 / 27 nodes** (goals **#24 / #24 / #23 / #26**) with **12 pocket charms** and per-volume state machines, the E2E section of `TEST_REPORT.md` and `tools/test_browser_e2e.py` still referenced the legacy V1.0 **17 / 17 / 16 / 23 node** topology (goals **#16 / #16 / #15 / #22**) and **3-charm** pool. In addition, several movement rule branches and event definitions conflicted between the specification, test report, and board definitions.

This document records every inconsistency across:
1. **Node Numbering & Board Topology** across all four volumes (`tokaido`, `yokai`, `kesshu`, `genji`).
2. **Movement Rule Branches** across all four volumes.
3. **Conflicting Event Definitions & State Payloads** across `mobile/js/boards.js`, `mobile/js/core.js`, `TEST_REPORT.md`, and `docs/GAME_DESIGN_SPEC_V1.1-V2.0.md`.

- **Inconsistencies Identified**:
  1. **`TEST_REPORT.md` (L49, L61) vs `boards.js`**: `TEST_REPORT.md` claimed `17` nodes (goal `#16`) and stated: `巻ノ弐：0 → 出目 3 → 查表跳至 4，并熄一盏青行灯`.
  2. **Legacy Mawari+Jump vs Historical Tobi Indexing**:
     - In `legacy` mode (`core.js` V1.1–V1.3), rolling `d` from `#0` first steps `d` squares along the chain (`0 + d`) and then adds `node.jumpTable[d - 1]`. Thus at `#0`:

## 2. Movement Rule Branch Inconsistencies Across the Four Volumes

| Volume | Rule Branch | `mobile/js/boards.js` + `mobile/js/core.js` Implementation | `TEST_REPORT.md` / Legacy Test Expectation | Resolution Applied |
|---|---|---|---|---|
| **Vol. I `tokaido`** | **Goal Overshoot & Secondary Landing Effect** | In `legacy` mode, overshooting `#24` from `#23` on roll `3` bounces 2 steps back to `#22 関宿・鈴鹿峠`, which has `jumpTable = [-3,-3,-3,-3,-3,-3]`, pulling the piece back `-3` to **`#19 新居関所`**. In `historical` mode (`ruleMode: 'historical'`), `landingInstruction` executes only on direct landings or once per turn (`#23` + roll `3` bounces to `#22`, then `#22` `returnTo` moves to `#19`). | Legacy `TEST_REPORT.md` expected `#15` + roll `3` $\rightarrow$ bounce off `#16` to `#14` with no secondary pullback. | Updated E2E test to start at `#23` with roll `3`, verifying both the `bounce` event at `#24` and the resulting position `#19`. |
| **Vol. I `tokaido`** | **Gourmet Coin Collection & Spend (`spendCoin`)** | Landing on `#2`, `#7`, or `#12` awards bitmask `1 / 2 / 4` and `+1` travel coin (`boardState.tokaido.coins[player]`). Spending 1 coin cancels a `stay` (`#4, #9, #17`) or negative checkpoint jump (`#14, #19, #22`). | Legacy E2E suite in `TEST_REPORT.md` did not test travel coins or `spendCoin`. | Added unit & E2E assertions for `#2` gourmet bitmask/coin grant and coin-cancel branch. |
| **Vol. II `yokai`** | **Ao-Andon Lanterns (`#4, #10, #16, #22`) vs Global Counter** | `core.js` tracks per-player bitmask `boardState.yokai.lanternMask[player]` across 4 specific lantern squares (`#4` bit 1, `#10` bit 2, `#16` bit 4, `#22` bit 8) and derives `state.lanterns = 4 - popcount(lanternMask[human])`. Completing all 4 bits arms `hyakkiPending[player] = true` for the next forward jump (`×2`, or `×3` with `lantern` charm). | Legacy `TEST_REPORT.md` L61 assumed *every* jump on Yokai decremented a global `yokaiLanterns` counter. | Aligned E2E test to roll `4` from `#0` (contacting lantern node `#4` and jumping `+2` to `#6`), verifying `lanternMask[0] == 1` and `lanterns < 4`. |
| **Vol. II `yokai`** | **Historical Tobi-Sugoroku (`dieDestinations`) vs Legacy Step+Offset** | In `ruleMode: 'historical'`, `yokai` uses pure `movementMode: 'tobi'`: roll `1..6` looks up `node.dieDestinations[roll]`; if `null`, the piece stays in place (`tobi_stay`). In `ruleMode: 'legacy'`, `yokai` steps `roll` squares first and then applies `jumpTable[roll - 1]`. | Not distinguished prior to V2.0 redesign. | Separated `ruleMode: 'historical'` (`dieDestinations` direct jump / `null` stay) from `ruleMode: 'legacy'` (`jumpTable` offset) and verified both in unit & E2E suites. |
| **Vol. III `kesshu`** | **Same-Square Clash (`kesshu_stance`) vs Coexistence** | In `ruleMode: 'legacy'`, landing on an opponent's non-start/non-goal square pauses with `pendingChoice.type = 'kesshu_stance'` (`assault` / `feint` / `defend`) or auto-resolves duel pushback + regalia steal, and requires `tokens == 7` to enter `#23`. In `ruleMode: 'historical'`, `allowSharedSquare: true` and `historicalRequiredTokens: 0` allow peaceful coexistence and direct entry into `#23`. | Legacy `TEST_REPORT.md` only tested automatic knockback and `#14 -> #15` goal lock. | Tested both `historical` (peaceful sharing on `#2` & direct win at `#23` with 0 tokens) and `legacy` (`kesshu_stance` choice pause, regalia theft, and `#23` goal lock/unlock). |
| **Vol. IV `genji`** | **Active Branch Choice at `#15 関屋` (`genji_branch`)** | In `core.js`, reaching or passing `#15 関屋` with `options.pauseOnChoice = true` sets `pendingChoice = { type: 'genji_branch', remainingSteps, ... }` so the player can choose `good` (`#16..#20`) or `evil` (`#21..#25`) regardless of die parity. When `pauseOnChoice` is `false`, even rolls take `good` and odd rolls take `evil`. | `boards.js` node `#15` caption previously stated only "even roll -> good, odd roll -> evil", contradicting `core.js` active route selection. | Updated `boards.js` `#15 関屋` rule description and verified both interactive `genji_branch` choice and non-interactive parity fallback in E2E tests. |
