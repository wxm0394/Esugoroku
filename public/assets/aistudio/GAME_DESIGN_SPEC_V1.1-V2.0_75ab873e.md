## 0. 文档目的与结论

本文件定义 Esugoroku 从当前版本演进至 V2.0 的玩法方向、规则边界、状态模型、实现顺序和验收标准。它是后续编码 Agent 的执行依据。若实现需要改变本文件中的规则，必须先更新本文件或建立明确的设计决议，不允许由 Agent 自行补全关键胜负规则。

### 0.1 当前版本判断

当前项目已具备：

- 四套独立的浮世绘主题棋盘与路线结构。
- 36 张锦绘收藏卡，以及开局被动 Buff 原型。
- 三种护符、同格冲突、武具收集、善恶双路线、妖怪跳跃表。
- 骰子动画、棋盘渲染、音效、图鉴、离线运行和浏览器 E2E 测试。
- JavaScript 规则引擎与旧版 C11 规则引擎。

当前最主要的产品问题不是内容数量不足，而是主动决策少、AI 与玩家的掷骰公平性不一致、部分玩法状态在 UI 层处理、两套规则引擎已不再保持同一规则。

### 0.2 核心产品定位

Esugoroku 应是一款以日本江户浮世绘与传统絵双六为表现核心的轻策略桌面游戏。

核心体验由四部分组成：

1. **骰子带来不确定性**：骰子决定移动结果，玩家不能控制随机结果。
2. **玩家管理不确定性**：通过路线、护符、锦绘 Buff 和特殊格选择降低风险或创造机会。
3. **棋盘主题决定策略**：四卷必须有不同的主要决策，不只是换皮。
4. **收集提供长期目标**：图鉴、成就、收藏和战绩推动重复游玩，但不得形成付费或纯数值碾压。

### 0.3 设计原则（必须遵守）

- 保留四卷现有视觉、布局、音乐和美术方向；玩法迭代不得以重做视觉系统为前提。
- 人类玩家与 AI 使用同一骰子规则、同一棋盘规则、同一护符规则。
- 所有影响胜负的逻辑由纯规则引擎计算，Canvas、DOM 和动画层只负责展示结果。
- 每卷必须至少存在一个具有实际收益/代价的主动选择。
- 单局策略应易于理解；不要把絵双六改造成复杂的 TCG 或 RPG。
- 新机制必须可被自动化测试，必须能解释为何触发、影响谁、持续多久、如何清除。
- 旧存档中的收藏和设置必须保留；更新不能悄悄清空玩家数据。
- 所有玩法离线可运行，不增加强制云服务、账号、追踪或在线依赖。

## 2. 全局规则契约（V1.1 必须先完成）

### 2.1 公平掷骰

**规则定义：**

- 所有玩家（人类、AI、本地双人）均使用 1–6 均匀分布的六面骰。
- 每次玩家回合只生成一个正式骰子结果；该结果是规则输入。
- 骰子动画必须表现该结果，但动画碰撞、帧率、窗口大小不能改变规则结果。
- AI 不得遍历 1–6 后挑选最大价值结果作为自己的骰点。
- AI 可以分析路线、使用战术、选择护符、决定分支或战斗姿态，但不能控制骰点。
- 测试环境允许注入可重复的 RNG / seed；正式游戏使用浏览器安全可用的随机源或经过验证的均匀随机实现。

**实现要求：**

- 将骰子生成抽象为统一接口，例如 `rollDie(rng) -> 1..6`。
- UI 的 `startRoll()` 负责请求结果并启动动画；规则引擎只接收结果，不调用随机函数。
- AI 与人类调用同一骰子入口。
- 测试可注入固定序列，确保结果可复现。

**验收：**

- 同一组 seed 与同一组玩家行动，必须生成完全相同的比赛结果。
- AI 不再存在遍历 1–6 后选出最大价值骰点的逻辑。
- 人类与 AI 的正式出目生成函数相同。
- 物理骰动画落定面与规则使用的出目一致。

### 2.2 回合阶段

统一使用以下阶段，不允许 UI 自行跳过规则状态：

1. **PRE_TURN**：检查玩家是否被跳过、护符是否恢复、是否有待处理选择。
2. **PRE_ROLL_CHOICE**：玩家可使用允许在掷骰前触发的战术或护符。
3. **ROLLING**：生成正式出目并播放骰子动画。
4. **RESOLVING**：按规则移动棋子、处理跳跃、目标、资源、冲突。
5. **PENDING_CHOICE**：若落点产生分支、路线或战斗选择，等待玩家决定。
6. **TURN_END**：记录历史、切换玩家、更新冷却。
7. **SETTLEMENT**：胜负或回合上限结算。

每次行动只能有一个确定的规则结果。动画播放期间不能重复提交、不能二次消费护符、不能重复推进状态。

### 2.3 规则处理顺序

每次正常掷骰按以下顺序处理。特殊格可以产生待选择状态，但必须明确暂停点。

1. 校验比赛未结束，当前玩家有效，骰点为 1–6。
2. 处理当前玩家的跳过回合；被跳过的回合不移动，但必须记录为一次行动。
3. 更新当前玩家自己的冷却/护符恢复计数。
4. 处理预先声明的移动 Buff（例如早駕籠、首回合加成）。
5. 沿当前有向路线移动，记录本次移动最终停下的接触节点（contact node）。经过但没有停下的节点不触发落点效果。
6. 若接触节点不是终点，先处理该节点的资源/收集特征（武具、名物、灯笼、怨念等）。每个玩家每个可收集特征按其独立领取规则结算。
7. 对接触节点执行一次出目查表跳跃；不得无条件无限连锁跳跃。接触节点上的停留/负面效果按节点数据定义执行。
8. 检查跳跃后的最终位置是否抵达终点、终点是否锁定、是否胜利；东海道同时执行点数一致/超越折返规则。
9. 在最终位置处理同格遭遇/决斗。
10. 如有主动选择，进入 PENDING_CHOICE；否则结束本回合。
11. 记录事件、状态快照和行动历史。

接触节点是本次真正停下并触发规则的节点；跳跃目的节点只改变棋子最终位置，不在同一回合递归触发目的节点的资源、停留或跳跃效果。终点检查和同格冲突仍按跳跃后的最终位置执行。这样可以让“名物/灯笼 + 妖怪跳跃”共存于同一节点，同时避免连续跳跃或重复领取。

### 2.4 同格冲突

- 四卷均保留同格遭遇机制，但冲突效果按卷区分。
- 起点格和终点格不触发普通同格冲突。
- 基础卷：被撞玩家后退 2 格。
- 英勇揃：进入战斗姿态选择，按 V1.2 规则处理。
- 只有英勇揃允许从对方身上夺取武具。
- 同格处理必须在事件记录中包含攻击者、被攻击者、前后位置、击退距离、是否夺取资源。
- 被击退位置不能小于起点；路线复杂化后必须通过路线历史或有向边规则正确回退，不得只用节点 ID 减法代替路径回退。

### 2.5 辻风奇袭统一规则

现有“辻风奇袭”保留为共通战术，但 V1.1 统一双方使用条件，避免 AI 与人类使用策略不对称：

- 只能在自己掷骰前使用。
- 只有当对手在有效路线进度上领先至少 3 格时才可使用。
- 将对手向后拉回 2 个路线节点；不可拉回起点之前。
- 目标处于终点或终点前的安全区域时不可使用。
- 每位玩家分别计冷却；冷却按该玩家自己的回合计算，不按全局半回合计算。
- 冷却初始为 4 个自己的有效回合；使用后重新计数。
- 人类和 AI 使用相同的资格判定函数。
- 如目标拥有“替身符”等防御效果，先处理防御，再决定奇袭是否成功。

若 V1.1 测试显示该战术在特定棋盘造成过强的逆转，应调节冷却或触发门槛，不得只对 AI 或人类单方面禁用。

### 2.6 回合上限与超时结算

棋盘数据中的 `maxTurns` 必须成为真实规则，不得只作为未使用的元数据。

- 全局以 **ply** 表示行动次数：任意一方完成一次回合即增加 1。
- 默认硬上限为 120 ply；四卷可在 100–140 ply 范围内单独调节，但初期统一使用 120。
- 达到上限仍未有人抵达终点时，进入超时结算。
- 超时判定先比较路线进度，再比较本卷目标资源，仍相同则平局。
- 不允许因跳过回合或动画卡顿无限延长比赛。
- 结算中必须显示“正常上り”或“回合上限判定”，不得把超时判定伪装成正常胜利。

路线进度应基于节点到终点的有效路径距离或显式 `progressValue`，不能简单用节点 ID 比较，因为分支路线的编号不一定代表实际距离。

### 2.7 预览与实际规则一致

当前预览与正式移动可能在护符、首回合加成、百鬼夜行倍率、终点锁定、同格冲突等方面产生差异。V1.1 要求：

- 预览必须调用与正式回合同一套纯模拟函数。
- 预览输入包括当前状态、玩家、骰点、待触发 Buff、跳跃倍率和有效路线选择。
- 预览不得真的消耗护符、增加回合数、修改历史或解锁收藏。
- 预览输出不仅是最终节点，还应包含路径、跳跃、是否休息、是否触发冲突、是否可能胜利。
- 如果某个分支/战斗决定尚未作出，预览应明确显示“需要选择”，不可猜测玩家选择。

### 2.8 唯一规则权威与 C11 处理

当前 JavaScript 规则引擎已包含扩展棋盘、Buff、战术奇袭和新玩法；C11 引擎仍是早期较小棋盘模型，双方并未保持完整镜像。当前 README/ARCHITECTURE 对“双规则完全一致”的描述必须修正。

**V1.1 决议：**

- 浏览器游戏以 `mobile/js/core.js` 作为运行规则权威。
- 所有影响胜负的状态必须从 core.js 的纯函数/规则 API 返回。
- main.js 不得自行改变玩家位置、资源、胜负、灯笼、名物、武具、道德值或冷却。
- main.js 只处理输入、动画、音画演出、HUD 和事件呈现。
- `core/esugoroku.c` 暂时保留为旧版独立规则原型，不再宣称与当前浏览器版本功能等价。
- C11 可在后续作为可移植规则引擎重建；重建完成前，C11 测试只能标注为 legacy regression，不得作为 JS 新功能的正确性证明。
- 更新 README、ARCHITECTURE、TEST_REPORT，明确实际测试对象和版本。

### 2.9 规则状态必须离开 UI 层

以下当前由 main.js 或全局 UI 状态管理的玩法数据，应迁移到比赛状态对象并由规则引擎修改：

- 东海道名物/旅钱。
- 妖怪卷的灯笼进度和百鬼夜行待用状态。
- 源氏卷的道德倾向、路线选择和路线奖励。
- 英勇揃的武具状态、夺取和战斗姿态。
- 护符充能、冷却、奇袭冷却。
- 回合上限与胜负判定。

`handleEvents()` 只能读取规则事件并播放声音、弹出印章、显示说明，不允许在遍历事件时再改变比赛规则状态。

### 2.10 建议的核心比赛状态字段

字段名称可按代码风格调整，但语义必须完整：

| 字段 | 含义 |
|---|---|
| boardId | 当前画帖 ID |
| players | 玩家类型、AI 难度、装备信息 |
| turn | 当前行动方 |
| ply | 全局已完成行动数 |
| playerTurnCount[2] | 每位玩家自己的已行动次数 |
| pos[2] | 两位玩家当前位置 |
| tokens[2] | 本卷资源/武具 bitmask |
| skip[2] | 待跳过的自身回合数 |
| charmLoadout[2] | 双方护符配置 |
| charmCooldown[2] | 双方各护符剩余自身回合冷却 |
| equippedCard[2] | 双方本局主将锦绘 |
| pendingChoice | 当前待处理的路线/战斗/道具选择 |
| boardState | 本卷专属规则数据 |
| winner | 胜者或未结束 |
| resultReason | 正常抵达、超时、退出等 |
| rngState | 可复现的随机状态/seed |
| history | 有序行动记录，支持回放与调试 |

boardState 的建议内容：

- 东海道：每位玩家的已收集名物 bitmask、旅钱余额。
- 百种怪谈：每位玩家已点亮/熄灭灯笼 bitmask、百鬼夜行是否待触发。
- 英勇揃：武具 bitmask、临时防御/战斗姿态。
- 源氏绘合：分支选择、善恶倾向值、怨念印记。

## 3. V1.2：共通战术系统

### 3.1 护符改为真正的构筑选择

护符从 3 种扩展为 12 种。每局每位玩家从可用护符中选择 3 种，不允许默认同时装备所有护符。原有三种保留。

| 护符 | 类型 | 规则 |
|---|---|---|
| 宿场守り | 防守 | 取消一次泊/休息造成的跳过回合 |
| 妖怪封じ | 防守 | 取消一次负向跳跃 |
| 早駕籠 | 移动 | 一次移动额外 +1 步 |
| 重骰符 | 随机管理 | 掷骰后、移动前可重掷一次；新结果必须接受，每局 1 次 |
| 替身符 | 防守 | 取消一次同格冲突的击退和资源夺取 |
| 反击符 | 反制 | 被同格攻击后，将攻击者向后推 1 格；每次充能触发一次 |
| 风行符 | 移动 | 掷骰前使用，本次移动 +2 步；不能与早駕籠在同一回合叠加 |
| 净心符 | 防守 | 取消一次跳过回合或负向跳跃（二选一，触发时选择） |
| 东海道旅券 | 卷专属 | 仅东海道可装备；开局获得 2 枚旅钱，可用于免除泊或取消一次关所后退 |
| 青行灯守 | 卷专属 | 仅百种怪谈可装备；点亮四处灯笼后，下一次正向怪异跳跃倍率从 2 倍提升到 3 倍，仅一次 |
| 旗本军配 | 卷专属 | 仅英勇揃可装备；第一次武具决斗中免疫武具被夺，之后消耗 |
| 和歌短册 | 卷专属 | 仅源氏绘合可装备；在善恶分岔处可先查看两条路线的近期风险摘要，再作路线选择；不直接增加移动数值 |

### 3.2 护符使用与恢复

- 每个护符有明确触发时机：掷骰前、掷骰后、落点时或被攻击时。
- 同一效果不得由两个护符在同一事件中重复抵消；优先级由规则引擎决定。
- 每位玩家分别维护充能/冷却，不能使用全局 turnCount 让对手回合替自己恢复。
- 普通自动触发型护符（宿场守り、妖怪封じ、早駕籠等）使用后，默认在拥有者完成 4 个自身回合后恢复 1 次充能。
- 明确标注“每局一次”的护符（重骰符）不自动恢复。
- 装备界面显示效果、触发时机、恢复条件和当前卷是否适用。
- 不允许在动画播放中重复点击导致重复消耗或重复触发。

### 3.3 主将锦绘（保留一张）

- 每位玩家每局装备 1 张已收藏锦绘作为主将。
- 主将只提供一个清晰的被动/开局 Buff，不构成抽牌战斗系统。
- 对局开始后锁定装备；换牌必须重新开始比赛。
- 主将 Buff 不得直接保证胜利，也不得让玩家越过本卷核心目标。
- 同一效果不可无限叠加；所有首回合加成只触发一次。
- 对不同画帖不适用的 Buff 必须有明确适配规则，不得静默产生无效字段。
- 对手 AI 也必须有合法主将配置；困难度只能改变选择质量，不能给 AI 隐藏数值加成。

### 3.4 Buff 平衡边界

- 开局前进最多 +2 节点。
- 单次移动额外步数最多 +2。
- 单次决斗击退强化最多 +2 节点。
- 初始武具不得直接满足英勇揃全部三种武具需求。
- 首次攻击/防守类 Buff 每局最多触发一次，除非明确写明冷却。
- 任一装备组合都不能同时获得“开局领先 + 大幅加速 + 免疫所有负面效果”。

## 4. 四卷专属玩法规格（V1.2 核心交付）

### 4.1 卷一：东海道——旅程资源与风险管理

**定位：** 旅行竞速。核心问题是“如何利用名物与旅钱，选择什么时候加速、什么时候规避风险”。

**保留现有规则：**

- 外周到内周的螺旋路线。
- 泊格造成休息。
- 名物格前进跳跃。
- 终点点数一致；超越终点折返。
- 同格冲突基础击退 2 格。

**新增规则：**

1. 三个名物格各自对应一个独立名物标记。每位玩家最多领取一次，不再由 UI 单独计数。
2. 首次落在名物格并完成效果后，获得 1 枚旅钱；每种名物每位玩家只能获得一次。
3. 旅钱上限为 3。
4. 玩家可在落入泊格时支付 1 枚旅钱，免除本次跳过回合；也可在关所后退效果触发时支付 1 枚旅钱抵消后退。一次事件只能支付一次。
5. 没有旅钱或选择保留旅钱时，原有负面效果正常生效。
6. 旅钱不可在终点直接兑换胜利；剩余旅钱只用于结算评分与成就。

**主动决策：**

- 泊格触发时，若有旅钱，弹出“支付旅钱继续”或“保留旅钱接受休息”。
- 关所后退触发时，允许选择是否支付旅钱。
- AI 根据到终点距离、旅钱数量、当前领先/落后程度决定是否使用旅钱。

**验收：**

- 同一玩家重复经过同一名物格不能重复领取旅钱。
- 对手的名物领取状态独立。
- 支付旅钱后不再产生该次泊/关所负面效果。
- 不支付旅钱时原有规则完整执行。
- HUD 展示名物收集和旅钱数量，结算展示剩余旅钱。

### 4.2 卷二：百种怪谈——灯笼探索与百鬼夜行

**定位：** 高波动路线风险管理。玩家需要决定如何利用怪异跳跃，并完成灯笼探索以获得一次强力爆发。

**保留现有规则：**

- 妖怪格使用 1–6 出目查表。
- 正向跳跃、停留和负向跳跃。
- 妖怪封じ可取消符合条件的负向跳跃。

**灯笼规则改造：**

1. 将四盏青行灯落实为四个明确的棋盘格特征，不再因“任意普通落点”减少全局灯笼计数。
2. 初始建议灯笼节点为 #4、#10、#16、#22；若实际布局或平衡测试要求调整，必须更新棋盘数据和测试。
3. 每位玩家独立维护自己的灯笼探索 bitmask；踩中某一灯笼格后，只有该玩家点亮自己的对应标记。
4. 同一玩家重复经过同一盏灯不能重复计数。
5. 集齐四盏灯后，该玩家获得一次“百鬼夜行待用”状态。
6. 在之后第一次触发正向妖怪跳跃时，跳跃距离 ×2，然后消耗待用状态。
7. 如果玩家在集齐四灯的同一回合触发正向跳跃，不立即使用；必须留到下一次正向妖怪跳跃，避免获得条件与消耗条件发生顺序歧义。
8. 负向跳跃、停留、普通移动不消耗百鬼夜行。
9. 百鬼夜行属于玩家个人状态，不因对手熄灯、触发或使用而影响。

**主动决策：**

- 玩家可在百鬼夜行待用时选择“立即用于下一次正向跳跃”或“保留”；默认自动用于下一次正向跳跃。
- 若装备青行灯守，触发后的下一次正向跳跃为 ×3；仍然只触发一次。

**验收：**

- 只有四个指定灯笼格能增加灯笼进度。
- 双方灯笼进度互不影响。
- 四灯集齐的玩家获得且只获得一次待用状态。
- 负向跳跃不消耗待用状态。
- 跳跃预览与实际倍率一致。
- 结算显示灯笼收集数、百鬼夜行是否触发。

### 4.3 卷三：英勇揃——三备え、战斗姿态与武具争夺

**定位：** 四卷中最具对抗性的玩法。核心是收集三种武具、控制风险，并在同格战斗中选择不同战术。

**保留现有规则：**

- 兜、太刀、陣太鼓三种不同武具。
- 至少持有三种不同武具才能上り。
- 棋盘上允许同一武具设置多个收集点，但重复取得不增加武具种类数。
- 同格冲突可击退对手；满足条件时可夺取对方持有而自己没有的武具。
- 终点未满足三备え时返回终点前一格。

**战斗姿态（V1.2）：**

当玩家与对手在非起点、非终点格发生同格遭遇，暂停结算并要求当前行动者选择一个姿态：

| 姿态 | 效果 | 适用场景 |
|---|---|---|
| 猛攻 | 将对手击退 3 格；若对手拥有自己缺少的武具，夺取其中一种 | 希望打断对手收集/冲线 |
| 牵制 | 将对手击退 1 格，不夺取武具；本方获得一次临时防护标记 | 资源已经领先，希望降低反击风险 |
| 固守 | 不主动击退；抵消对手可能触发的反击效果，并保留本方已有武具 | 武具齐全、接近终点时保守推进 |

**具体限制：**

- 每次遭遇只能选择一种姿态。
- 每种姿态必须有事件记录。
- 猛攻夺取武具时，从“对手拥有且自己没有”的集合中选择一种；若只有一种则自动夺取。
- 没有可夺取武具时，猛攻仍然击退 3 格，但不产生资源事件。
- 被替身符保护时，本次击退和夺取均取消。
- 同格姿态由当前移动者选择；AI 使用相同的合法选项。
- 决斗不允许把对方推过起点，也不允许直接推入终点。

**验收：**

- 三种姿态的击退、夺取、防护差异可自动测试。
- 只有英勇揃触发武具夺取。
- 兜、太刀、陣太鼓三种 bitmask 规则正确。
- 重复收集同一种武具不改变种类数。
- 未集齐三备え时不能获胜。
- AI 能按局势选择姿态，而不是总选择猛攻。

### 4.4 卷四：源氏绘合——善恶分岔与风险收益

**定位：** 路线选择和结局倾向。玩家主动选择雅道或修罗道，骰子不再替玩家决定道德路线。

**改造规则：**

1. 玩家到达 #15 分岔格后，将分支状态保存为待选择。
2. 在下一次移动开始前，玩家选择“雅道（善）”或“修罗道（恶）”。
3. 分支选择一旦确认不可随意反悔；只有指定护符或特殊规则可以改变。
4. 移动时从所选分支继续，不再根据骰子奇偶选择。
5. 保留现有善道与恶道的独立节点和各自特殊效果。

**路线平衡方向：**

- 雅道：风险较低、停留/后退较少、进度更稳定；奖励偏向荣誉和收藏。
- 修罗道：风险较高，保留负向跳跃和停留；沿途可收集怨念印记，完成后可换取一次小型战术效果或专属成就。
- 两条路线应有接近的期望完成回合数；不能让善道在所有情境下明显优于恶道。
- 路线差异必须来自事件概率和资源收益，而不是简单地让一条路线多走很多格。

**道德倾向：**

- genjiBalance 从 HUD 装饰状态改为规则状态。
- 走雅道增加善德倾向；走修罗道增加修罗倾向。
- 落在特定善/恶节点可进一步改变倾向。
- 道德倾向影响结算称号、收藏解锁和战役分支，不直接替代正常胜负条件。
- V1.2 单局结算先展示路线与倾向；V2.0 战役再让倾向影响后续章节。

**验收：**

- #15 不再由骰子奇偶自动决定路线。
- 玩家与 AI 均能明确提交分支选择。
- 选定路线后移动路径与预览一致。
- 两条路线的状态、奖励、结算称号互不混淆。
- genjiBalance 由规则引擎维护，不由 HUD 更新。

## 5. V1.3：锦绘收藏、解锁与长期成长

### 5.1 收藏定位

36 张锦绘首先是艺术收藏品，其次才是可装备的主将 Buff。收藏进度不应依赖付费、随机抽卡或必须击败高难度 AI。

### 5.2 初始收藏与兼容

- 保留现有默认收藏名单和用户已有收藏。
- 现有存档中的卡片不可因升级变成未收藏。
- 新玩家继续获得当前版本定义的起始收藏卡。
- 开局选择画帖不得直接解锁该卷全部九张卡。
- 对局结束、完成任务或达成成就时，才根据明确条件解锁卡片。

### 5.3 每卷九张卡的解锁框架

每卷 9 张卡按三层目标安排：

| 卡位 | 解锁条件类型 | 目的 |
|---|---|---|
| 01–03 | 起始收藏/新手引导 | 初始可玩，不阻止体验 |
| 04 | 首次完成该卷 | 鼓励走完路线 |
| 05 | 首次击败普通 AI | 奖励胜利 |
| 06 | 完成该卷核心机制目标 | 鼓励体验独有玩法 |
| 07 | 完成一个进阶目标 | 鼓励重复游玩 |
| 08 | 困难 AI 胜利或等价挑战 | 提供熟练度目标 |
| 09 | 大师挑战/特殊成就 | 收藏终极目标 |

核心机制目标示例：

- 东海道：收集至少 2 种名物并使用一次旅钱。
- 百种怪谈：集齐四灯并触发百鬼夜行。
- 英勇揃：持有三种武具获胜，并至少完成一次战斗姿态选择。
- 源氏绘合：完成任意分支路线并达成指定善恶倾向。

具体卡号与任务映射写入数据配置，不在渲染代码中硬编码。

### 5.4 成就与战绩

每卷至少提供：

- 初次完成。
- 首次获胜。
- 完成核心机制。
- 无护符胜利。
- 困难 AI 胜利。
- 大师挑战完成。

个人战绩至少记录：

- 总局数、胜/负/平。
- 各卷局数与胜率。
- 最短获胜 ply。
- 最多一次收集的资源数量。
- 决斗次数与成功夺取次数。
- 已收藏卡片数量。
- 已完成成就数量。

### 5.5 存档

- 从 `esugoroku.profile.v1` 迁移到带版本号的新结构。
- 迁移时合并已收藏卡、装备卡、音效/BGM 设置。
- 迁移失败时回退到安全默认值，但不得覆盖原始 v1 数据。
- 收藏、装备、成就、战绩在关键事件后自动保存。
- 保存当前未完成对局属于 V2.0，不要求 V1.3 完成。
- 提供“重置战绩/重置全部数据”的不同操作，并要求二次确认。

## 6. AI 规格

### 6.1 公平性

AI 与人类同规则：

- 同样的骰子生成规则。
- 同样的节点效果。
- 同样的护符和 Buff 充能。
- 同样的回合上限。
- 同样的待选择规则。
- 不得读取未来 RNG 结果。
- 不得通过隐藏加速、隐藏护盾或更高掉落率补偿难度。

### 6.2 难度等级

| 难度 | 决策方式 | 目标体验 |
|---|---|---|
| 简单 | 合法选项中偏随机选择，少量主动使用护符 | 轻松体验主题 |
| 普通 | 使用规则启发式评估路线、资源与领先差 | 标准对局 |
| 困难 | 比较自己行动后的局面，并估算对手下一回合的风险 | 有竞争力 |
| 大师 | 使用有限深度 Expectiminimax/随机博弈搜索，兼顾对手反制 | 追求最优战术 |

### 6.3 决策边界

AI 可决定：

- 是否使用辻风奇袭。
- 是否使用可主动使用的护符。
- 进入分岔时选择哪条路线。
- 英勇揃遭遇时选择战斗姿态。
- 是否支付旅钱或消耗一次性资源。
- 装备阶段选择哪张已解锁主将锦绘和哪三种护符。

AI 不可决定：

- 自己的骰子点数。
- 对手的合法选择。
- 尚未发生的随机事件结果。

### 6.4 搜索与性能

- V1.2 先实现确定性启发式决策，不要求一次达到大师级。
- V1.3 引入有限深度随机博弈搜索，先以“当前行动 + 对方下一行动”作为基线。
- 对骰子概率节点取期望，对玩家选择节点取最大值/最小值。
- 估值考虑有效路线进度、胜利概率、资源、剩余护符、跳过回合、可用战术和对手威胁。
- 采用搜索节点上限和超时保护，搜索超限时回退到启发式策略。
- AI 思考结果必须可复现，不能因动画帧率而改变决策。

## 7. V2.0：完整游戏模式

### 7.1 四卷巡览战役

增加一个“巡览四卷”的章节模式，将四卷作为四个主题篇章，而不是按历史年代硬凑成一条时间线。

- 第一章：东海道旅程——旅行、名物与关所。
- 第二章：百种怪谈——探索灯笼、遭遇怪异。
- 第三章：英勇揃——武具、决斗与军阵。
- 第四章：源氏绘合——善恶路线与结局倾向。

章节之间使用简短画帖序言、收藏记录和结果摘要连接。每章可设置普通目标与额外挑战。

战役继承内容优先为收藏、称号、图鉴、剧情记录；不要把上一章的永久数值 Buff 带入下一章造成雪球优势。

### 7.2 本地双人

- 支持同一设备轮流操作（Pass-and-Play）。
- 双方分别选择护符和主将锦绘。
- 轮到另一方时显示明确的交接提示，可隐藏上一方的装备选择摘要。
- 双方掷骰规则一致。
- 第一阶段不做在线网络联机。
- AI 模式保持不受双人模式影响。

### 7.3 挑战模式

提供可重复的固定挑战：

- 固定棋盘、固定初始位置、固定资源和固定随机 seed。
- 目标可以是限回合获胜、指定护符获胜、完成全部资源收集、在落后情况下逆转等。
- 每项挑战有明确规则说明和通过条件。
- 挑战记录保存本地，不需要网络排行榜。

### 7.4 回放与续局

- 记录比赛 seed、初始配置、每次骰点、护符使用、路线选择和战斗选择。
- 回放通过重新执行规则事件生成，不保存每一帧动画。
- 允许从本地存档恢复未完成比赛。
- 若版本升级导致规则变化，旧回放必须标记使用的规则版本，不得用新规则伪装为旧结果。

## 8. 技术实施约束

### 8.1 模块责任

| 模块 | 责任 | 禁止事项 |
|---|---|---|
| `mobile/js/core.js` | 纯规则、模拟、事件、胜负、AI 输入输出 | DOM、Canvas、音频、直接随机调用 |
| `mobile/js/boards.js` | 棋盘图数据、节点特征、护符/卡片配置 | 在 UI 层计算效果 |
| `mobile/js/state.js` | 应用状态、配置、存档读取/迁移 | 另行实现一套游戏规则 |
| `mobile/js/main.js` | 输入、流程调度、动画、事件视觉化 | 直接改规则资源或胜负 |
| `mobile/js/ui_screens.js` | 画帖选择、装备、分支/战斗选择、结算 UI | 决定规则效果 |
| `tools/test_js_rules.mjs` | 规则、棋盘数据、AI 和存档相关测试 | 只测试 UI 文案而不测规则 |
| `tools/test_browser_e2e.py` | 浏览器流程、输入、视觉状态、回归测试 | 代替纯规则测试 |

### 8.2 建议核心 API

可在不破坏现有接口的前提下逐步演进：

- `createMatch(boardId, options)`
- `applyRoll(board, state, roll, options)`
- `applyChoice(board, state, choice)`
- `applyCharm(board, state, charmId, timing)`
- `applyTacticalAction(board, state, actionId)`
- `simulateTurn(board, state, roll, options)`
- `previewOutcomes(board, state, options)`
- `getLegalChoices(board, state)`
- `evaluateState(board, state, player)`
- `validateBoard(board)`

规则函数必须尽量纯函数化：输入状态不被原地修改，返回新状态、事件列表、是否进入待选择和胜负结果。

### 8.3 棋盘数据

每个节点除位置和视觉字段外，使用可组合的规则特征，例如：

- features: stay、jump、token、lantern、gourmet、branch、goal。
- jumpTable: 六个出目对应的相对效果。
- next: 有向边。
- prev 或路线历史策略：用于回退。
- choice: 分支/事件选择定义。
- progressValue 或可计算的终点距离：用于超时判定与 AI 估值。

不得只用单一 kind 字段表达多个同时存在的效果。例如百种怪谈某格既有妖怪跳跃，又是青行灯节点时，应该可以同时拥有两个 feature。

### 8.4 事件契约

事件至少包含：

- type
- player
- from
- to
- roll
- source
- payload

每个规则状态改变必须有对应事件。UI 根据事件播放演出，不可根据 HUD 当前文案反推规则。

### 8.5 旧存档兼容

- 引入明确的 profile schema version。
- 迁移函数必须幂等：重复执行不会重复解锁或重复增加统计。
- 对已收藏卡采用集合并集，不得清空旧收藏。
- 对已装备但已失效的配置回退到合法默认值，并向玩家显示提示。
- 存档损坏不能导致页面无法启动。

## 11. 设计决议摘要（给 Agent 的不可擅自更改项）

1. AI 不得选择骰子点数；所有玩家同规则掷骰。
2. JavaScript core 是当前浏览器版唯一规则权威；C11 在重新实现前标记为 legacy。
3. 规则状态不得由 main.js、HUD、Canvas 或动画层修改。
4. 四卷的独特机制必须保留，不能合并成同一套通用棋盘。
5. 每局每位玩家最多装备 3 种护符和 1 张主将锦绘。
6. 四盏青行灯必须是明确棋盘节点，双方独立累计。
7. 源氏善恶路线改为玩家/AI 主动选择，不再由奇偶数自动决定。
8. 英勇揃必须保留三种武具作为终点门槛，战斗姿态不能绕过此条件。
9. 收藏采用确定性解锁，不自动一次性开放整卷全部卡片。
10. V2.0 首先实现离线战役、本地双人和回放，不承诺在线联机。
11. 新规则必须同步更新数据、纯规则测试、E2E、README 和架构文档。
12. 不得为了通过测试而删除原有玩法或弱化测试断言；规则变更必须有对应设计解释。

## 12. 实施完成的定义

一个版本只有同时满足以下条件才算完成：

- 玩家能在游戏中理解新增机制。
- 规则引擎能独立、确定性地执行新增机制。
- AI 能合法使用新增机制，但不获得骰子或资源特权。
- 单元测试覆盖正向、负向、边界和重复触发。
- 浏览器 E2E 覆盖玩家实际操作流程。
- 旧存档、收藏和设置不会丢失。
- 文档与当前实现一致。
- 在离线环境中仍可运行。

**最终产品目标：** 玩家记住的不是“我又掷了一个六点”，而是“我在东海道保留旅钱躲过关所，在百种怪谈集齐四灯，在英勇揃夺回太刀，在源氏绘合主动走上修罗道”。骰子制造故事，玩家的选择决定故事如何发展。
